# Open questions

Each item is an assumption I made so Phase 1 could proceed while you were away. None blocks the work. Each says what I did and what to tell me if you want it different.

## Phase 1

1. **Pricing removed from Phase 1.** SPEC section 9 includes a pricing stub in Phase 1; the instruction for this run excluded pricing. I followed the instruction. Confirm that the pricing engine moves to a later phase, and which one.
2. **AISC file layout is unknown.** The catalog loader takes the name column, weight column and weight unit as explicit arguments instead of guessing header names. When you supply the file, tell me its headers (or let me read it) and I can add defaults. The weight unit has no default on purpose.
3. **Weight conversion.** If the file gives lb/ft, `weight_kg_per_m` is stored as lb/ft x (0.45359237 / 0.3048), the exact definitional conversion. Confirm you want kg/m as the stored weight and not an AISC metric column.
4. **Column supports.** SPEC says a member with no support is flagged, and `supported_by` lists member ids. Columns normally bear on foundations, not on other members. Default: columns are exempt from the "unsupported" flag (their `supported_by` references are still checked). Everything else needs at least one valid reference. Tell me if columns should also be flagged, or if a "foundation" marker should exist.
5. **Severity mapping.** red = the member cannot be weighed or its geometry is wrong (profile missing or not in catalog, non-positive weight or length, missing elevation, length unavailable). amber = the weight can be computed but the record is incomplete or suspect (material or grade missing, unsupported, bad support reference, duplicate). The worst issue sets the member status. Confirm or give me your mapping.
6. **Profile matching is exact.** The validator checks `member.profile` against catalog names with exact string equality. Turning `profile_raw` (for example "W18x35") into a catalog name is the job of extraction (Phase 2 to 4), not the validator, so nothing is silently normalized here.
7. **Duplicate rule.** Same type, same profile and the same two resolved end points (either direction, exact numeric equality, no tolerance). Every member in a duplicate group is flagged, and none is dropped. Members with no profile or no resolved end points are not compared.
8. **Length source.** Length is the 3D distance between `resolved_xyz_mm` of the two ends. If either is missing the length is "unavailable" (flagged red), not estimated from grids.
9. **Not implemented because they need your input:** material/grade plausibility per shape family (SPEC section 6) and the scale-based length sanity check. Tell me the plausibility table and I will add the rule.
10. **Rejected members.** Review status `rejected` cannot occur until Phase 3. For now every member returned by the project is included in the BOM. Decide in Phase 3 whether rejected members are excluded.
11. **Contract details I had to choose** (SPEC section 5 leaves them open). Confirm or correct:
    - `bbox` is `{x0, y0, x1, y1}` in page coordinates; the coordinate system is defined in Phase 4a.
    - Project `grids[].axis` is `'x'` or `'y'`; `unit_system` is the literal `'mm'` (pending the section 12 question).
    - `review` is `{ status, edits: [{ field, original_value, corrected_value, reviewer, timestamp }] }`; in Phase 1 `edits` is always empty.
    - Every key is required, and unknown values are explicit `null` (so a missing material cannot be mistaken for "not provided").
12. **Excel units.** Lengths are shown in mm and feet-inches (nearest 1/16 inch); weights in kg and lb, plus metric tonnes in the Summary. No short/long "tons" are used because the word is ambiguous. Tell me if you want different columns or units.
13. **Included-but-flagged members. RESOLVED (2026-10-07, your decision):** RED members are excluded from the main total and reported on a separate "excluded (red)" line; AMBER stays in the main total.
14. **"Column has no base elevation" (Phase 1 follow-up), my reading.** The base is the lower end of the column, chosen by the resolved z coordinate when both end points are resolved (a tie picks the start), otherwise the lower of the two elevations. The new red issue `COLUMN_BASE_ELEVATION_MISSING` is raised when that end has no elevation or the ends cannot be ranked. If only the top elevation is missing, only `MISSING_END_ELEVATION` (or `..._START_...`) is raised, because the base is still known. Columns remain exempt from the unsupported-member check. Tell me if you meant something else (for example a separate foundation level).

16. **Classification keyword map (my defaults).** schedule: SCHEDULE / MEMBER, BEAM or COLUMN LIST. plan: FRAMING or TRELLIS together with PLAN. detail: DETAIL, SECTION, CONNECTION. notes: NOTES, SPECIFICATIONS, ABBREVIATIONS, LEGEND, SYMBOLS, COVER, INDEX, DRAWING LIST. other: any other PLAN (site, foundation, floor), ELEVATION. Several different kinds in one title (for example "FRAMING PLAN AND DETAILS") -> priority schedule > plan > detail > notes, confidence 0.5, flagged. No evidence -> `other`, confidence 0, flagged. Confirm or give me your own map.
17. **Single sheet scale rule.** A page has a parsed sheet scale only if exactly one distinct scale expression is found. Several (typical for plan sheets with detail callouts) or none -> no parsed scale, all found scales are stored and the sheet is flagged, and you set the override. Tell me if you want a preference rule (for example the scale nearest the title block).
18. **Scale ratio meaning.** ratio = real length / drawn length, so 1/8" = 1'-0" is 96, 1" = 20' is 240, 1:50 is 50. NTS has no ratio. Manual override accepts the same forms, exactly one scale per override.
19. **No authentication yet.** The override request must carry an `editor` name (stored with the edit); there is no login. SPEC section 12 (auth model) is still open.
20. **Project `status` values** are now `created`, `scanning`, `scanned`, `scan_failed`. Approval states are added in Phase 6. The project form accepts only `unit_system = mm` (SPEC section 12, canonical unit, still to be confirmed) and the server sets the status.
21. **Duplicate sheet numbers.** The unique index on (project, sheet_number) from migration 001 is dropped: the number is extracted text, not an identity. Duplicates are kept and flagged `duplicate_sheet_number`; the page index is the identity.
22. **Thresholds are tunable defaults, not measured values:** text layer >= 20 characters, vector drawing >= 50 paths, scanned = one image covering >= 50% of the page with too few vector paths, low classification confidence < 0.7.

## Phase 4b

23. **`font_id` meaning and default.** A glyph library belongs to a `font_id`: one CAD font as exported by one firm/tool. Default `default` (config `GLYPH_FONT_ID`); the `read-text` request can name another. Nothing detects the font automatically, so two different fonts under one id would mix their shapes. Tell me how you want ids assigned (per firm, per project, per CAD export).
24. **Which sheets are read.** `read_text` reads sheets the scan marked `vector` (including drawings without a text layer) and skips `scanned` and `unknown` pages. Only upright lines of at least 2 characters become text items; single stray characters (for example a lone `1` in a triangle) are counted as unassigned, not stored. Tell me if single characters should become items.
25. **Re-reading replaces items.** `read_text` deletes and rebuilds a project's `text_items` (they carry no user edits yet; keys are stable). `glyph_library.seen_count` is cumulative over reads (for ranking only), so re-reading the same sheet raises it again.
26. **Case.** Library labels are upper case; a letter is lower case if shorter than 0.8 x the cap/digit height of its line. A real lower-case-only shape that differs from its capital still needs its own group and label. Mixed-case text beyond that is untested.
27. **OCR vote scope.** Votes only come from lines whose OCR length equals the cluster count, so lines with small marks (dots, apostrophes, `=`) never vote and those marks must be labeled by you without OCR help. Vote proposals fold letters to upper case.
28. **OCR model licence (needs your decision).** The model files ship without a licence text (docs/OCR_DEPENDENCY_REVIEW.md). Fine for internal use in my view; confirm upstream before any distribution, or tell me to drop the OCR group.
29. **Confidence values are constants,** not calibrated probabilities (0.8 glyph only, 0.3 unknown shapes, 0.95 OCR agrees, 0.5 OCR disagrees). Say if you want different numbers.
30. **`POST read-text` was added** (not in your list) because the job needs a way to be started; it only enqueues `read_text` for a project whose scan is done and refuses duplicates while one is queued or running.
31. **Schema proposal waits for approval:** docs/SCHEMA_CHANGE_PROPOSAL.md, section 8 lists the five questions.
32. **AISC catalog not supplied yet.** Profile validation compares canonical names (uppercase, no spaces, `X`, fractions and decimals equal only by exact numeric value) with `catalog_shapes.shape_name`. When the AISC file arrives, confirm which column holds the nomenclature; the importer already takes column names as arguments. Until then every profile is `unvalidated`.
33. **Pipe, plate, rod naming.** Canonical forms `PIPE4STD`, `PL1/2X8`, `ROD3/4` are my convention, matched to the catalog only by exact name. Say if your catalog or estimating practice uses other forms.
34. **Sheet-number rules fail on one document layout** (0 of 16 pages, `docs/PHASE4D_COVERAGE.md`): its title block is not in the assumed corner or strip. Needs a decision on whether to learn more layouts or leave those pages to review.
35. **Titles are only taken next to a TITLE label** and are not found at all in two of the six documents; same question.
36. **Multi-scale pages** (most pages have several scales) stay `multiple_scales` for review; mapping a scale to its view is not attempted.
37. **Text-quality threshold (0.90)** that decides pdf_text versus the glyph reader is a tunable default, not measured. No page in the six documents fell below it.
38. **Rotated pdf_text items** are stored with their angle (`angle_deg`) and read normally; they are not flagged for review. Say if rotated text should always be reviewed.

## Phase 5b

48. **Long lines carry several labels, so lengths may be overstated (needs your decision).** On job-005, 190 members sat on 105 drawn lines; 28 lines carried more than one member (113 members), and in 111 of those the labels have DIFFERENT profiles and are spread along a line that is on average longer than the others (median 432 pt against 266 pt). This looks like one drawn line standing for several beams end to end (or a line crossing several members), not one beam labelled twice. Each member gets the whole line length, so the takeoff length is overstated for them. The shared-line rule holds all but the best-scoring one out of the main total until a person decides; splitting a long line between its labels is a new design and is not done. Which do you prefer: (a) the person splits the line by clicking, (b) a rule splits it at the label positions, (c) keep the counts and measure those members by hand?
49. **The shared-line flag is a hold, not a verdict.** Of 106 linked gold labels in the six documents (study classes), 40 sit on a shared line and only 20 of those 40 (50%) have the right line, against 48 of 66 (73%) for labels alone, so the flag is informative. But holding the second and later members out of the main total undercounts when they are real separate members. The first line of the takeoff shows how many pieces are held.
50. **Fixed margin for the whole-sheet view.** There is no reliable title block rule across the documents, so the box leaves 2.5% on every side and the far-right 14%. A title block along the bottom is not excluded. Do you want a per-firm template, or a draw-the-box default instead?
51. **Only framing plans are in the takeoff by default.** The Phase 4e study found that picking pages by profile counts chose real framing plans only 17 of 31 times, and the page type guess is the same kind of guess, so some real framing sheets will start as "not in the takeoff" until a person includes them. The harness had to switch 6 of the 24 calibration pages. Is it better to default to include and let a person exclude?
52. **Joist designations are checked by form only.** K, LH and DLH are recognised by pattern; depth and series numbers are not checked against the SJI tables (no table is invented here). A joist is never matched to AISC and has no weight in this phase. Give me the SJI table if joists should be validated.
53. **"Not a member" reasons** are existing, misc steel, detail, other (as you listed). Existing steel is left out of the takeoff entirely; say if existing steel should be listed separately instead.
54. **Grades are typed per shape family** and never default. Materials such as A992 or A500 are not applied automatically even where the general notes say so. A person types them once per family.
55. **The first calibration found a real bug: the "use these classes" choice was not kept.** The link job replaced a person's structural class choice with its own suggestion (fixed in Phase 5b, commit "Fix: choosing the member line classes is now a confirmation"). On job-004 the suggested class gives 3 of 20 labels right and the study's classes 8 of 20. Class suggestion is the weak point of the flow on mixed-linework documents (wood and steel on one sheet). Should every view start by asking the person to confirm the line classes?
56. **The calibration views were made by the test harness, not a person**, and the gold is AI-made. job-009 page 16 has no scale on the sheet; the harness assumed one for the parity run only (lengths there mean nothing).
57. **The column schedule is a two-column table that the row-based legend builder cannot read** (see docs/PHASE5C_COLUMN_SCHEDULE_NOTES.md). Do you want the column-aware parser as Phase 5c, and composite plan tags split in the same phase?
